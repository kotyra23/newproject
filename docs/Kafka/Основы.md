# Apache Kafka (DevOps Handbook)

## 1. Краткая суть
**Apache Kafka** — распределенная платформа потоковой передачи событий (event streaming).  
⚠️ **Важно понимать:** Это не классическая очередь (сообщения не удаляются после прочтения, а хранятся по времени/размеру) и не реляционная база данных (нет сложных запросов, оптимизирована под последовательную запись и чтение).

## 2. Ключевые понятия
* **Broker:** Экземпляр сервера Kafka (нода кластера).
* **Topic:** Логическая категория данных (аналог таблицы в БД).
* **Partition:** Физический раздел топика. Обеспечивает параллелизм. **Порядок сообщений гарантируется ТОЛЬКО внутри одной партиции.**
* **Offset:** Уникальный инкрементальный ID сообщения внутри партиции.
* **Consumer Group:** Группа потребителей. Каждая партиция топика назначается **только одному** активному потребителю внутри группы (это механизм балансировки нагрузки).
* **KRaft (Kafka Raft):** Современный режим работы кластера без ZooKeeper (стандарт для Kafka 3.3+).

## 3. Критические параметры конфигурации (`server.properties`)
Эти параметры чаще всего становятся причиной инцидентов.

| Параметр | Рекомендуемое значение (Prod) | Описание и подводные камни |
| :--- | :--- | :--- |
| `listeners` | `PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093` | На каких интерфейсах брокер **слушает** входящие соединения. `0.0.0.0` означает "все интерфейсы". |
| `advertised.listeners` | `PLAINTEXT://<DNS_имя_или_внешний_IP>:9092` | **САМАЯ ЧАСТАЯ ПРИЧИНА ОШИБОК!** Адрес, который брокер отдает клиентам для подключения. Если здесь `localhost`, клиенты с других машин получат таймаут. |
| `log.retention.hours` | `168` (7 дней) | Сколько времени хранить сообщения перед удалением. |
| `log.retention.bytes` | `-1` (или лимит, напр. `10737418240`) | Макс. размер данных на партицию. При достижении старые сообщения удаляются. |
| `default.replication.factor`| `3` | Количество копий данных по умолчанию. Для Prod минимум 2, лучше 3. |
| `min.insync.replicas` | `2` | Мин. кол-во синхронизированных реплик для подтверждения записи (работает в паре с `acks=all` у продюсера). |
| `auto.create.topics.enable`| `false` | **Всегда выключать в Prod!** Топики должны создаваться явно через CI/CD или админку, чтобы избежать опечаток и мусора. |

## 4. Шпаргалка по CLI (`bin/kafka-*.sh`)

### Управление топиками
```bash
# Создать топик
kafka-topics.sh --bootstrap-server kafka1:9092 --create --topic my-topic --partitions 3 --replication-factor 3

# Список всех топиков
kafka-topics.sh --bootstrap-server kafka1:9092 --list

# Детальная информация (лидеры, реплики, ISR - in-sync replicas)
kafka-topics.sh --bootstrap-server kafka1:9092 --describe --topic my-topic

# Удалить топик
kafka-topics.sh --bootstrap-server kafka1:9092 --delete --topic my-topic

##Тестирование (Producer / Consumer)

# Отправить сообщения (ввод с клавиатуры, Ctrl+D для отправки строки, Ctrl+C для выхода)
kafka-console-producer.sh --bootstrap-server kafka1:9092 --topic my-topic

# Прочитать сообщения с самого начала
kafka-console-consumer.sh --bootstrap-server kafka1:9092 --topic my-topic --from-beginning

##Управление Consumer Groups (Критически важно!)

# Список всех групп потребителей
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 --list

# Статус группы (показывает LAG - отставание потребителей от продюсера)
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 --describe --group my-consumer-group

# Сброс offset'ов группы на самое начало (ТРЕБУЕТ ОСТАНОВКИ консьюмеров этой группы!)
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 --group my-consumer-group --reset-offsets --to-earliest --execute --topic my-topic



##5. Мониторинг и Алертинг

Используйте Prometheus + JMX Exporter или Kafka UI. Настраивайте алерты на следующие метрики:


🚨 Under-replicated partitions > 0: Есть партиции, у которых не хватает синхронизированных реплик. Риск потери данных при падении ноды.

🚨 Consumer Lag (отставание): Потребитель не успевает читать данные. Резкий рост лага = деградация бизнес-сервиса.

🚨 Offline partitions > 0: Партиция недоступна для чтения/записи (серьезный сбой кластера).

⚠️ Свободное место на диске (log.dirs): Алерт при > 80% заполнения. Если диск заполнится на 100%, Kafka остановится и может повредить данные.


##6. Troubleshooting (Решение частых проблем)

❌ Ошибка клиента: Connection refused или Timeout

Проверьте, слушает ли порт на брокере: ss -tlnp | grep 9092

Проверьте сеть с машины клиента: nc -zv <kafka-ip> 9092

Главная причина: Проверьте advertised.listeners на брокере. Если там localhost или внутренний IP, недоступный клиенту, клиент получит этот адрес и попытается подключиться к нему, получив таймаут.

❌ Ошибка клиента: KafkaTimeoutError: Timeout waiting for future (Python/Java)

Топик не существует, а auto.create.topics.enable=false.

Брокер перегружен (высокий CPU или медленный диск) и не отвечает в течение request.timeout.ms.

Несовпадение cluster.id или node.id при настройке KRaft кластера (брокеры не могут собрать кворум).

❌ Диск заполнен на 100%, Kafka не запускается

Временно освободите место вручную (удалите старые .log или .snapshot файлы в log.dirs).

Уменьшите log.retention.hours или log.retention.bytes.

Для топиков, где важны только последние значения ключей, включите Log Compaction: cleanup.policy=compact.


##7. Golden Rules для DevOps (Best Practices)

Забудьте про ZooKeeper. Новые кластера разворачивайте только в режиме KRaft.

Никогда не используйте replication-factor=1 в Production. При падении одной ноды вы потеряете доступ к данным. Минимум 2, идеально 3.

Всегда используйте DNS-имена (например, kafka1.internal), а не жестко заданные IP-адреса в advertised.listeners. Это спасет при миграции ВМ или смене IP.

Выделяйте Kafka отдельные диски. Желательно NVMe/SSD, так как Kafka крайне чувствительна к IOPS и задержкам записи (fsync).

Не храните секреты (пароли, токены) в топиках. Kafka не шифрует данные "из коробки" (требуется настройка TLS/SASL и шифрования на уровне приложения).
